- [x] **H-02 — `OriginButton` computed safety attributes can be overridden by consumer props.** — RESOLVED 2026-11-25: conflicting props are stripped from `rest`; computed `role`/`tabindex`/`aria-disabled`/simulated-button attributes are authoritative; E2E override case added.
  - Evidence: `packages/origin/src/primitives/button/Button.astro:106-110` spreads `{...computedAttrs}` before `{...rest}`; `role` and `tabindex` are inherited from `HTMLAttributes<"button">` at line 26.
  - Mechanism: later JSX spreads win, so `<OriginButton as="span" role="link">` type-checks but renders `role="link"` while the simulated-button keyboard script still attaches; `tabindex` and `aria-disabled` can be overridden the same way.
  - Impact: silently defeats the action/navigation invariant (`AGENTS.md:22`) and the simulated-button keyboard contract.
  - Fix applied: strip `role`, `tabindex`, `aria-disabled`, `data-lsui-simulated-button`, and `data-icon-only` from `rest` in `Button.astro` (Astro emits duplicate attributes and the browser keeps the FIRST one, so spread order alone is insufficient); spread computed attrs last. `buttonAttrs()` also emits `undefined` for conflicting native-button attributes. Playground E2E asserts native/simulated/disabled overrides are neutralized.

- [x] **H-03 — `OriginLink` disabled-link attributes can be overridden by consumer props.** — RESOLVED 2026-11-25: `role`/`tabindex`/`aria-disabled` stripped before rendering; disabled links keep `role="link"`, `aria-disabled="true"`, and no `href`.
  - Evidence: `packages/origin/src/primitives/button/LinkButton.astro:83-86` spreads `{...computedAttrs}` before `{...rest}`; `aria-disabled` is inherited from `HTMLAttributes<"a">` at line 23.
  - Mechanism: `<OriginLink disabled aria-disabled="false">` renders without `href` (from `linkAttrs`) but with `aria-disabled="false"`, so assistive tech sees an inconsistently disabled link.
  - Impact: contradicts the documented disabled-link contract (`AGENTS.md:22`, `LinkButton.astro:10`) and can break focus/pointer guard behavior.
  - Fix applied: `LinkButton.astro` destructures `aria-disabled` out of `rest` and deletes `role`, `tabindex`, and `data-icon-only` at runtime (since `role` is intentionally absent from its Props type); `linkAttrs()` emits `undefined` for conflicting keys on active links. Playground E2E asserts a disabled link with hostile props still renders `role="link"`, `aria-disabled="true"`, and no `href`.

- [x] **H-04 — `announce()` fallback reintroduces the modal-inert live-region bug it was designed to avoid.** — RESOLVED 2026-11-25: fallback region is now hosted inside an open dialog/popover (or the body), keyed by host; scheduled via `doc.defaultView`; detached targets skipped; forced-fallback E2E/unit coverage added.
  - Evidence: `packages/origin/src/announce.ts:60` appends the fallback region to `doc.body`; lines 115-119 use the global `requestAnimationFrame` rather than `doc.defaultView`; line 114 clears text before scheduling.
  - Mechanism: a body-level `aria-live` region becomes inert while a top-layer `<dialog>` or `[popover]` is open — the exact scenario `ariaNotify()` was chosen for (`FINDINGS.md` ariaNotify entries). An iframe `doc` override also schedules the update on the parent window. Calling before `doc.body` exists would throw.
  - Impact: announcements silently lost in modal flows on pre-Baseline-2026 browsers and in iframe consumers.
  - Fix applied: `fallbackRegions` is keyed by host `Element`; `findFallbackHost()` prefers an open `<dialog>` or `[popover]:popover-open`, then `doc.body ?? doc.documentElement`. Scheduling uses `doc.defaultView?.requestAnimationFrame` with a `setTimeout` fallback; a detached `target` is skipped; a missing host is a no-op. `packages/origin/tests/announce-fallback.test.ts` deletes both `ariaNotify` methods and asserts the region lands inside an open dialog with the right text.
